## 1. 結論

typesafe.ai の調査から、次の2件を実装する。

1. **A1 確信度による3段階フィードバック。** ジェスチャーが成立したとき、どれくらい余裕をもって成立したかを0〜1の確信度にし、演出の強さを「全開」「控えめ」「無音」の3段階に分ける。追跡切れは3段階とは別に、今までどおり手位置の案内を出す。判定の合否と P1 の記録は変えない。外部AIは使わない。
2. **B1 テスター自由記述の自動仕分け。** 実機確認レポートの自由記述（印象に残った動作、分からなかった場面、無視された場面、痛みや不快感）を、typesafe.ai の Jev に「選択肢から1つ選ぶ」形で仕分けさせ、確信度0.9以上だけを自動集計する。それ未満は人が読む。ゲーム本体には入れず、開発者のPCで動かす道具にする。

どちらも、README の次の作業である Android Chrome の実測が終わるまで着手しない。A1 は判定の閾値を変えないが、フィードバックの変更は試験条件の変更にあたるため、両端末の比較が終わってから Phase 2 の一部として作る。A1 の対象動作は、Phase 2 へ持ち込む動作（README の次の判断で3〜4動作へ絞る）が決まってから確定する。本書で5動作を並べている箇所は、その決定までの候補一覧である。

## 2. 目的

### 2.1 A1 の目的

- iPhone 実測で Bloom は6/10だった（[14](./14_p1_session_analysis_20260916063846360.md)）。失敗4件はすべて試行の時間切れで、うち2件は準備の時間切れ、残る2件は準備完了後の時間切れだった。後者2件には `bloom-not-outward`（両手が外向きに開く動きになっていない。コード上は内向きへ戻る動きを検出したときの理由）が記録された。今の画面は、成立か不成立かの二値しか返さないため、プレイヤーは「どれだけ足りなかったか」を知る手段がない。
- 惜しい動き（距離が少し足りない、左右の同期が少し離れた）に「入ったが浅い」と返せれば、閾値を緩めなくてもプレイヤーが自分で直せる。実測の2件が「惜しい」に入るかは診断リプレイで確認する（5章の2）。入らなくても、控えめ段階の目的は変わらない。
- 04 の6章「タイミングが近い: 演出量を少し抑える」と 06 の5章「部分成立を成功音と同じ強さで鳴らさない」は、段階を付ける方針をすでに持つ。ただし段階を決める軸が決まっていない。A1 はその軸を確信度に統一する。
- 「プレイヤーを罰しない」を保つ。どの段階も否定の音・文言・赤表示を出さない。

### 2.2 B1 の目的

- 05 の9章の主観質問と、実機確認レポートの自由記述は、Phase 4 で5人以上が複数回遊ぶと手作業の限界を超え始める。
- 01 の13.1「『曲を自分で開放した』と表現される」は自由記述からしか読めない成功指標で、今は集計手段がない。
- Jev は文字の分類に特化し、確信度を返す。確信度で「自動集計」と「人が読む」を分ければ、人の判断を残したまま作業量を減らせる。

## 3. 現状の確認（2026-09-18 時点のコード）

### 3.1 確信度の今の扱い

各状態機械は成立イベントに `confidence` を付けているが、式は動作ごとの手作りで、根拠のある較正はしていない。

| 動作 | 現在の式（`src/gestures/*-state-machine.ts`） | 問題 |
|---|---|---|
| air-tap | `0.6 + speed / 3` | 絶対速度を使う。06 の6章「絶対速度や腕の長さは使わない」と合わない |
| ribbon-swipe | `0.55 + pathDistance + Math.max(0, directionalSpeed) * 0.12` | 速度を含む。距離は正規化座標なので可 |
| Bloom | `0.58 + outward * 0.8 + upward * 0.8 + min(0.25, speed * 0.08)` | 閾値との差ではなく絶対量。同期幅を含まない |
| Lift | `0.6 + upwardDistance * 0.8 + min(0.2, speed * 0.08)` | 同上 |
| Spotlight | `0.62 + min(1, heldMs / (holdMs * 2)) * 0.3` | 保持時間だけ |

旧clap／burst（`clap-burst-state-machine.ts`）も `confidence` を付けるが、履歴扱いのため A1 の対象にしない。

使い道は `src/gestures/gesture-arbiter.ts` の調停（同時に出た候補の順位付け）の最後の基準だけで、演出、記録の集計、分析には使っていない。成立イベントが出るのは全条件を満たしたときだけなので、確信度は常に0.55以上になり、「惜しい」動きは拒否（`GestureRejection`）として理由コードだけが残る。

成立イベントの `quality` に記録されている値は動作ごとに違う。既存の JSON から較正できる範囲は、この記録で決まる。

| 動作 | 記録済みの `quality` | A1 の要素として追加が要るもの |
|---|---|---|
| air-tap | `speed` | 面の通過位置の中心からの距離、通過後に抜けたか |
| ribbon-swipe | `speed`、`pathDistance`、`perpendicularError`、`direction` | なし |
| Bloom | `outwardDistance`、`upwardDistance`、`syncSpreadMs`、`speed`、`preparationSpan` | なし |
| Lift | `upwardDistance`、`syncSpreadMs`、`speed` | 横ずれ |
| Spotlight | `holdDurationMs`、`spotlightVariant` | 上下ゾーンへの入り込みの深さ |

### 3.2 自由記述の今の置き場

`src/testing/device-checklist.ts` の実機確認レポート（schema 2.3）にある自由記述欄と、B1 で扱うかどうかを次に示す。

| 欄 | 内容 | B1 の対象 |
|---|---|---|
| `subjective.unclearMoments` | 何をすべきか分からなかった場面 | 対象 |
| `subjective.ignoredMoments` | 分かって動いたのに無視されたと感じた場面 | 対象 |
| `subjective.memorableAction` | 一番印象に残った動作 | 対象 |
| `subjective.painOrDiscomfort` | 痛みや不快感 | 対象 |
| `notes` | 自由メモ | 対象 |
| `decision.nextChange`、`decision.reason`、`decision.nextFixedConditions` | 作成者が書く判断の記録 | 対象外。テスターの言葉ではない |

数値欄（同期感1〜5、疲労0〜10、もう一度遊びたいか）はすでに構造化されているので、B1 の対象にしない。レポートは JSON として保存され、`?view=analysis` の画面で PC から読み込める。読込は schema 1.0（移行あり）と 2.0〜2.3 に対応している。

## 4. A1 の設計

### 4.1 変えないもの

- 状態機械の閾値、成立条件、`GestureEvent` と `GestureRejection` の既存フィールド。
- P1 の合否判定と P1 の結果 JSON（schema v7）。A1 は P1 の画面に入れない。
- 05 の8章の分類（success／player miss／machine miss／false trigger／tracking loss／unclassified）。段階は表示の話で、分類の話ではない。
- 04 の追跡喪失時の案内（該当側の光を薄くして「手を少し内側へ」）。追跡切れは3段階に混ぜず、案内を残す。
- 06 の10章「同じイベント記録を再生すると同じ Resonance になる」。段階は記録済みの値だけから決める純粋関数にするので、再生しても同じ段階になる。

### 4.2 確信度の定義

確信度は「各条件を、閾値に対してどれだけ余裕をもって満たしたか」を0〜1にした値の合成とする。Jev の「要素ごとに別々に問い、コードで重み付けする」という流儀に合わせ、要素ごとの値を残す。

各要素の余裕は次で求める。

```text
margin(value, threshold, comfortable) = clamp01((value - threshold) / (comfortable - threshold))
```

- `threshold` は今の閾値（例: Bloom の `minimumOutwardDistance = 0.16`）。変えない。
- `comfortable` は「余裕をもって成立した」と見なす値。初期値は iPhone 実測の成功イベントの `quality` 値の中央値から置き、Android の実測後に両端末の値で見直す。
- 上限のある条件（同期幅、保持前のぶれ）は向きを反転して同じ式を使う。

要素の合成は「最も余裕のない要素」を重く見る。

```text
confidence = 0.6 * min(margins) + 0.4 * mean(margins)
```

絶対速度は要素に入れない。06 の6章（表現点は絶対速度や腕の長さを使わない）、01 の7.3（叩く強さ、腕の絶対的な伸び、身長や腕の長さに依存する移動距離を評価しない）、02 の3.5（絶対ピクセル距離ではなく手幅・キャリブレーション範囲へ正規化する）に合わせるためである。ただし「動きが遅すぎる」拒否（`movement-too-slow`）は現状のまま成立条件として残す。

| 動作 | 要素（すべて正規化座標か時間） | 備考 |
|---|---|---|
| air-tap | 面の通過位置の中心からの距離、通過後に止まらず抜けたか | どちらも `quality` に未記録。追加してから較正する |
| ribbon-swipe | 経路長、方向の一致（`perpendicularError` の反転）、中心通過 | 既存 JSON から較正できる |
| Bloom | 外向き距離、上向き距離、左右の同期幅（反転） | 既存 JSON から較正できる |
| Lift | 上昇量、左右の同期幅（反転）、横ずれ（反転） | 横ずれは未記録。追加してから較正する |
| Spotlight | 保持時間、上下ゾーンへの入り込みの深さ | 深さは未記録。追加してから較正する |

この表は Phase 2 へ持ち込む動作が決まる前の候補一覧であり、採用された動作にだけ実装する。

### 4.3 3段階と追跡切れの扱い

| 段階 | 条件 | 返し方 | 記録と採点 |
|---|---|---|---|
| 全開（`full`） | 成立イベントで `confidence ≥ 0.6` | 光、音、スケール変化を全部返す | success。06 のタイミング点＋ジェスチャー点＋表現点 |
| 控えめ（`soft`） | 成立イベントで `confidence < 0.6`、または部分成立の拒否（4.4） | 音は鳴らし、光を小さくする。否定は出さない | 成立イベントなら success で、06 の5章の部分成立（10点候補）の対象になり得る。拒否なら不成立のままで加点しない |
| 無音（`silent`） | それ以外の拒否、時間切れ | 何も出さず、ノーツを静かにほどく | 不成立 |
| 追跡切れ（段階外） | `tracking-lost` | 演出は出さず、04 のとおり該当側の光を薄くして手位置を案内する | 判定不能。06 のとおり分母から外す |

境界の0.6は Jev の文書が勧める「高0.9／中0.5〜0.9／低0.5未満」を出発点にした仮置きで、Phase 2 の実測で決める。「全開」が9割を超えるなら境界を上げ、「控えめ」が半分を超えるなら `comfortable` を下げる。

### 4.4 部分成立の拒否

06 の5章にある「一方だけの到達」「方向または中心通過の一方だけ」を、拒否の理由コードから決める。各状態機械が出す理由コードをすべてどちらかへ入れる。

| 動作 | `soft` にする拒否 | `silent` のままの拒否 |
|---|---|---|
| air-tap | なし（単一条件のため） | `movement-too-slow`、`cooldown-active` |
| ribbon-swipe | `off-axis`（方向は合っていて帯から少し外れた） | `wrong-direction`、`candidate-timeout` |
| Bloom | `bloom-outward-distance-insufficient`、`bloom-upward-distance-insufficient`、`bloom-sync-expired` | `bloom-not-outward`（内向きへ戻った）、`bloom-not-upward`（下向きへ戻った）、`movement-too-slow` |
| Lift | `lift-distance-insufficient`、`lift-sync-expired` | `lift-not-ready`、`lift-not-upward` |
| Spotlight | `spotlight-pose-not-held` | `spotlight-wrong-side`、`spotlight-wrong-zone`、`spotlight-hands-not-separated`、`spotlight-pose-before-go` |

`tracking-lost` は 4.3 のとおり段階の外で扱う。

`soft` の拒否は、同じ試行の中で1回だけ返す。拒否は毎フレーム近く連続して記録される（iPhone 実測の ribbon-swipe では `wrong-direction` 43件と `candidate-timeout` 2件が連続記録された。どちらも `silent` 側だが、`off-axis` のような `soft` 側の拒否でも同じ連続が起きうる）ため、そのまま音にすると連打になる。

### 4.5 置き場所

```text
src/gestures/feedback-tier.ts        純粋関数。GestureEvent または GestureRejection と閾値設定から
                                     { tier, confidence, factors } を返す
src/gestures/gesture-types.ts        FeedbackTier 型と GestureFeedback 型を追加。GestureEvent は変えない。
                                     未記録の要素を quality へ追加する場合は optional で足す
src/poc/phase2-*                     Phase 2 の統合シーケンス側で tier を演出へ変換する
```

状態機械の `confidence` 式は、A1 の関数が安定した後に同じ計算へ置き換える。それまでは並存させ、調停の順位付けは今の値のままにする。

## 5. A1 の実装順序

1. **正本の更新（コードより先）。** まず 03 の Phase 2 の成果物に3段階フィードバックを加えてよいかを決め、必要なら 03 を更新する。次に 04 の6章に3段階と追跡切れの扱いと「否定を出さない」を書き、06 の5章の「10点候補」を `soft` の成立イベントに対応付ける。02 の8.6（表示と採点の分離）に、段階は表示にだけ効くと書く。
2. **既存データで較正。** iPhone セッション `p1-20260916063846360` の成功イベントのうち、`quality` に要素が記録されている ribbon-swipe、Bloom、Lift、Spotlight に 4.2 の関数を当て、動作ごとの `confidence` 分布と段階の分布を出す。air-tap と未記録の要素は、`quality` へ追加した後のセッションで測る。Bloom の失敗2件（`bloom-1`、`bloom-3`）は診断リプレイで、`soft` 対象の拒否が出ていたかを確認する。Android の同条件セッションが取れたら同じことをして、`comfortable` の初期値を両端末の値から決める。結果は本書の10章に記録する。
3. **純粋関数と単体テスト。** `feedback-tier.ts` を作り、`tests/helpers/gesture-fixtures.ts` の合成イベントで、全開・控えめ・無音の境界、追跡切れが段階の外に出ること、絶対速度が結果に影響しないこと、同じ入力で同じ段階になることを確認する。
4. **Phase 2 画面への接続。** Phase 2 の統合シーケンス（03 の Phase 2 の成果物）で、段階ごとの効果音と光の量を割り当てる。カメラを隠した手の可視化と同じ画面に置く。
5. **Phase 2 記録への追加。** Phase 2 のセッション記録に、成立イベントごとの `confidence` と段階、試行ごとの `soft` 拒否の回数を残す。P2 ゲートの「machine miss 90秒に2回以下」の確認に、`soft` 拒否が多い動作を機械側の問題の候補として並べる。
6. **ブラウザ自動試験。** 合成の手で3段階の表示が出ること、否定の文言がないこと、追跡切れで手位置の案内が出ることを e2e に足す。
7. **実測での境界の見直し。** Phase 2 の2人×3回で、段階の分布と主観質問の「無視されたと感じた場面」を突き合わせ、境界を一度だけ変える。

## 6. B1 の設計

### 6.1 変えないもの

- ゲーム本体（`src/`）に外部通信を入れない。B1 は `scripts/` の Node.js の道具にする。
- 判定、採点、分類（05 の8章）に Jev の答えを使わない。B1 が扱うのは人の言葉だけ。
- 最終判断は人が行う。確信度が高い答えも、集計表に「自動」と印を付けて残し、人が上書きできるようにする。

### 6.2 送るものと送らないもの

| 送る | 送らない |
|---|---|
| 3.2 で対象にした自由記述の本文 | ランドマーク、座標、成立時刻差などの数値 |
| 質問の文面と選択肢の説明 | `sessionId`、`testerId`、端末名、User-Agent |
| 動作の名前 | 画面録画、映像、音声。作成者の判断欄（`decision.*`） |

送る前に、本文から端末名や人名らしい語を機械的に取り除くことはしない。代わりに、テスターへ「自由記述は分類のため外部のAIサービスへ文字として送ることがある」と事前に伝え、同意欄を実機確認レポートに足す（6.6）。同意がないレポートはスクリプトが送らない。

### 6.3 質問の設計

Jev の流儀に合わせ、1つの記述に対して独立した小さな質問を並べる。動作の選択肢は「Phase 2 で採用した動作＋該当なし（`none`）」に固定し、採用が決まるまでは本書に動作名を固定しない。

| 質問キー | 種類 | 内容 | 使い道 |
|---|---|---|---|
| `memorable_gesture` | Choice | 印象に残った動作はどれか（採用動作＋`none`） | 03 の体験ゲート「Bloom またはリボンスワイプを自発的に挙げる」 |
| `self_authored` | Noul | 「自分で曲を動かした・開放した」感覚を述べているか | 01 の13.1 の成功指標 |
| `confusing_gesture` | Choice | 何をすべきか分からなかった動作はどれか（採用動作＋`none`） | 動作見本の改善対象 |
| `ignored_gesture` | Choice | 正しく動いたのに無視されたと感じた動作はどれか（採用動作＋`none`） | P2 ゲートの machine miss の突き合わせ |
| `pain_location` | Choice | 痛みや不快感の部位（shoulder／arm／wrist／eyes／head／none） | 01 の9章の負荷管理 |
| `wants_retry` | Noul | もう一度遊びたいと述べているか | 数値欄 `retryIntent` との一致確認 |

選択肢の説明は、Jev の文書が勧める `what`／`not_for`／`examples` の構造で書き、例文は日本語にする。`examples` には Phase 2 の実際の記述を使い、個人が特定できる語を含めない。

### 6.4 確信度の扱い

| 確信度 | 扱い |
|---|---|
| 0.9以上 | 自動集計の列に入れる。表には「自動」と印を付ける |
| 0.5以上0.9未満 | 「要確認」の列に入れ、Jev の答えを候補として併記する。人が確定する |
| 0.5未満 | 答えを表示せず「未分類」にする。人が読む |

Noul は確率そのものが返るため、0.85以上を「はい」、0.15以下を「いいえ」、その間を「要確認」にする。境界は Phase 2 の精度試験（6.5）で見直す。

### 6.5 精度試験（使うかどうかを決める前に行う）

日本語は英語より精度が落ちると公式が明記しているため、先に精度を測る。

1. Phase 2 の2人×3回のレポート（3.2 の対象5欄×6件＝最大30件）を、作成者が先に手で仕分けて正解表を作る。
2. スクリプトを1回だけ走らせ、答えと正解表を比べる。
3. 判断基準: 確信度0.9以上の答えのうち正解が9割以上、かつ確信度0.9以上で不正解が1割以下。この2つを満たさなければ、Phase 4 では使わず、記述を手で読む。
4. 満たさない場合に一度だけ試す変更: 質問と選択肢の説明を英語にし、例文だけ日本語のままにする。それでも満たさなければ打ち切る。

### 6.6 置き場所と形式

```text
scripts/classify-tester-comments.mjs   実機確認レポート JSON を読み、質問を組み立て、
                                        API を呼び、集計表（Markdown）と生の答え（JSON）を書き出す
scripts/lib/typesafe-request.mjs        質問の組み立てと確信度の振り分け。API を呼ばない純粋関数
tests/typesafe-request.test.ts          組み立てと振り分けの単体テスト。通信は行わない
```

- API キーは環境変数 `TYPESAFE_API_KEY` から読む。リポジトリと結果ファイルには書かない。
- 通信は Node.js 22 の `fetch` で `POST https://api.typesafe.ai/v1/systemone` を直接呼ぶ。公式 SDK（`@typesafe-ai/sdk`）は Node.js 専用で機能も同じなので、依存を増やさない。採用する場合は版を固定する。
- 出力には、モデルの版（`jev-1.13.0`）、実行日、質問の文面、各答えの確信度をそのまま残す。同じ入力でも答えが変わりうるため、出力を分析文書（`docs/1x_*`）に貼るときは実行日を添える。
- 429（回数制限）と529（過負荷）は指数バックオフで3回まで再試行し、それでも失敗した記述は「未送信」として表に残す。
- 実機確認レポート（schema 2.3）に `consent.externalTextClassification: boolean` を足し、schema 2.4 にする。1.0（移行あり）と 2.0〜2.3 の読込は今までどおり残し、欄がないレポートは「同意なし」として扱う。

### 10.1 較正の下調べ（2026-09-19）

`src/` を変えずにできる範囲として、保存済みの P1 結果 JSON を読むだけの分析スクリプトを作った。アプリのビルドID（`src/` の内容から計算する）は変わらないため、Android を後で同じビルドで測る条件を崩さない。ただし同日の[16](./16_structure_review_and_lightweight_fixes.md)の修正で `src/` が変わり、ビルドIDは変わった。端末間を同じビルドで比べるには、16 以降のビルドで両端末を測る。

```text
node scripts/analyze-p1-confidence.mjs <P1結果JSON> [複数可]
```

出力は動作ごとの、現在の `confidence` の分布、`quality` の各要素と閾値の関係、4.2 の式を当てた新しい確信度と段階の件数（`comfortable` を成功の下位25%点・中央値・上位25%点に置いた3通り）、拒否の理由ごとの段階と連続をまとめた回数、成功しなかった試行に控えめ対象の拒否があったか、である。schema v5 以降の `trialDiagnostics`（v6 では連続をまとめた `count` を展開して数える）と、旧 v2 の `rejections` の両方を読む。閾値はスクリプト内に写しを持つので、状態機械の既定値を変えたらスクリプトも直す。

**対象の iPhone セッション `p1-20260916063846360` の JSON は、2026-09-19 時点で作業PCに見つからなかった**（14 が記録した `Downloads` に無い）。このため、5章の2の本番の較正は未実施である。ファイルを再入手したら上のコマンドを実行し、結果を 10.2 として追記する。

スクリプトの動作は、schema v5 の形を模した手作りの検証用データと、作業PCに残っていた旧セッション `p1-20260720055054080.json`（schema v2、air-tap 10件と ribbon-swipe 3件だけの途中保存、旧ビルド）で確認した。旧セッションは端末もビルドも今と違うため、`comfortable` の決定には使わない。

下調べで分かったこと:

| 分かったこと | 根拠 | 計画への影響 |
|---|---|---|
| 今の `confidence` は下限が高く、上限に張り付く。段階の軸には使えない | 式と閾値から求めた下限は air-tap 約0.72、ribbon-swipe 約0.83、Bloom 約0.78、Lift 約0.74、Spotlight はほぼ0.77の固定値。旧セッションの実測でも ribbon-swipe は3件すべて1.0、air-tap は10件中6件が1.0 | 境界0.6を今の式に当てると全件が「全開」になる。4.2 の式へ置き換える方針を維持する |
| Spotlight の `holdDurationMs` は段階の要素にならない | 成立イベントは保持が `holdMs`（300ms）に達した瞬間に出るため、記録値は常に300ms強になる（`spotlight-state-machine.ts`） | Spotlight を採用する場合、3.1 の表のとおり「上下ゾーンへの入り込みの深さ」を `quality` へ追加するまで、全件を「全開」として扱う |
| air-tap は既存の記録から較正できない | `quality` は `speed` だけ | 3.1 の表のとおり。通過位置の記録を追加してから測る |
| ribbon-swipe は既存の記録だけで段階が分かれる | 旧セッション3件で、`comfortable` を中央値に置くと確信度は0.70〜1.00、上位25%点に置くと0.49〜0.71 | 式と3通りの `comfortable` の比較は機能する。件数が少ないので値は採用しない |
| 拒否は1回の操作で何十件も記録される | 旧セッションの ribbon-swipe で `off-axis` 104件、`wrong-direction` 36件 | 4.4 の「控えめの拒否は同じ試行で1回だけ返す」を維持する |
