## 旧clap分析当時の改善仮説と優先順位（履歴）

profileの現行値は[POCテスト手順](./05_poc_test_protocol.md)の3.2（`gpu-640x480-30`）である。

### P0: 次回試験で条件を揃える

1. 今回はiPhone Safariで`gpu-640x480-30`を使っている。iPhoneの基準比較を行う場合は、正本で指定された`baseline-gpu-640x480-60`を別sessionIdで実施する。
2. 保存時viewportが`393 × 735`なので、試行中が横向きだったかを記録する。縦向きで実施していた場合は、今回の結果を基準比較へ直接使わない。
3. profile、build、閾値は1セッション中に変更しない。
4. clap-1〜5の実接触では、画面の動作見本どおり「肩幅程度から中央へ、手のひらをそっと合わせる」を再確認し、実施者の主観記録を残す。
5. timeout時に、可能なら既存UIの手動分類で`player-miss`、`machine-miss`、`tracking-loss`、`unclassified`を選ぶ。timeoutを一括で機械失敗と扱わない。

### P1: 実接触clapの診断を増やす

次のコード変更候補は、閾値変更より先に以下の観測値を試行別に保存すること。

- 最後に両手が見えた時刻と、再取得までの欠落時間
- 最小手のひら距離と、その時の手ID・左右判定
- 接近速度、`triggerDistance`到達時刻、`contactLikeDistance`到達の有無
- 試行ごとの0手／1手／2手フレーム数
- 接触直前のidentity conflict回数と、再取得前後のtrack ID
- `occlusion-predicted`が成立／不成立になった理由

これにより、「物理的な接触で遮蔽されたが推定条件に届かなかった」のか、「手が十分に近づかなかった」のか、「ID競合で状態機械が継続できなかった」のかを分離する。

### P2: その後に判定またはUXを調整する

P1の観測結果に応じて、変更は一度に一項目だけ行う。

- 遮蔽が主因なら、手IDの再取得と`occlusionGraceMs`周辺を検証する。
- 接近速度不足が主因なら、動作見本と「止めずにそっと合わせる」説明を見直す。
- 十分に近づいているのに閾値未達なら、`contactLikeDistance`または`triggerDistance`を候補にする。ただし、誤トリガー計測を同時に行う。
- `clap-8`のような遅延が続く場合は、合図の視認性、準備時間、動作開始タイミングを確認する。offsetは推論遅延ではないため、MediaPipe高速化だけでは解決しない。

## 第三入力の方向転換（2026-09-14）

ここまでの実接触clap／near-clapの実機分析と`clapDiagnostic`の記録は、旧実験の履歴として変更しない。一方、現行P1／MVPの第三入力は、実接触の成立率を追加調査する方針からBloomへ切り替えた。

Bloomは、中央寄りの二手準備から左右それぞれ外側かつ斜め上へ開く入力である。実接触、クラップ音、マイク許可を要求せず、外向き距離、上向き距離、左右の閾値到達時刻の同期を判定する。短い追跡欠落は候補を継続し、長い欠落は`tracking-lost`を一度だけ記録して再アームする。準備中の動きは認識windowへ持ち越さない。

この方向転換は2026-09-14時点の決定である。その時点の標準結果はschema v4で`gestureVocabulary.thirdGesture = "bloom"`を明示し、schema v2／v3の旧clap結果は読み込めるが、比較画面と合否候補では旧clapとBloomを混在させない。その後、[13](./13_p1_five_gesture_50_trial_revision_plan.md)により5動作・50試行、schema v5へ改訂した。現行の実機出口は[POCテスト手順](./05_poc_test_protocol.md)の5章に従う。
