# 空間ジェスチャー音楽ゲーム POCテスト手順

- 更新日: 2026-09-19
- 文書種別: Phase 1 / Phase 2の実施手順・記録・合否定義
- ステータス: v0.8（追跡の途切れの許容をフレーム間隔に合わせ、ribbon-swipeの逆方向判定を後退距離だけにした。Bloomの案内の始点を下げた。根拠は19。v0.7: 定例の試行を残る2動作・20回へ絞り、試験手順をURLで選べるようにした。結果JSONをschema v7へ上げ、端末情報と処理経路の指定を記録項目へ追加。動作の切り替わりを画面のタップで進める。判定の閾値と合否は変えていない。v0.6: schema v6で性能値と向きを追加）
- 正本範囲: POCテストの条件、分類、記録、ゲート判定

## 1. 目的

このテストは市場性を証明するものではない。次の二点を、同じ条件で繰り返し確認する。

1. 普通のスマートフォンのインカメで、二手と3入力（air-tap／ribbon-swipe／Bloom）を再現可能に認識できるか。Phase 1では候補動作のLift／Spotlightも同じ条件で測り、Interaction POCへ持ち込む動作を選ぶ材料にする。
2. 音との反応差が、音楽ゲームとして不快な水準になっていないか。

## 2. 対象とデータ方針

- 初期テスター: 制作者本人、ターゲット属性に近い1名
- 端末: iPhone 15、Google Pixel 10 Pro XL
- 主な組み合わせ: ターゲットテスター／iPhone 15、制作者／Google Pixel 10 Pro XL
- 端末を入れ替えるクロス試験: 初回ゲートの必須条件ではない。OS差と個人差を分ける必要が出た場合に追加する
- 生映像・生音声: 原則保存しない
- 保存対象: 派生ランドマーク、イベント、時刻、性能値、回答、画面録画（同意がある場合のみ）

10代の参加者については、参加者本人へ目的、保存項目、共有範囲、削除方法を平易に説明する。年齢、地域、テストの実施形態に応じて必要な保護者確認を行う。画面録画やデバッグ映像を第三者へ共有する場合は、テスト参加への同意とは別に確認する。

## 3. 固定する試験条件

| 項目 | 初期条件 |
|---|---|
| 姿勢 | 椅子に座る |
| 端末 | スタンドへ横置き |
| 距離 | カメラから70〜100cm。実測値を記録 |
| カメラ | インカメ |
| 音声 | 本体スピーカー。Bluetooth禁止 |
| 照明 | 顔と手に正面または斜め前から光が当たる一般室内 |
| 背景 | 手と極端に同化しない背景。柄・逆光の有無を記録 |
| 服装 | 長袖／半袖、袖色を記録。試行中は変更しない |
| ブラウザ | ブラウザ名と完全なバージョンを記録 |
| OS | OS名と完全なバージョンを記録 |
| 音量 | 会話より少し大きい一定値。端末の音量段階を記録 |

条件を変えた試験は同じ結果表へ混ぜず、別セッションとして記録する。

### 3.1 修正後P1-Controlled再試験の基準プロファイル

2026-07-29に、修正後のiPhone SafariとAndroid Chromeで最初に行う30試行（3入力版）の基準条件を次で固定した。両端末とも同じアプリbuildと`baseline-gpu-640x480-60`を使い、端末ごとの結果を比較できるようにする。この表は3入力・30試行の時点の決定として残す。

| 項目 | 固定値 |
|---|---|
| profile ID | `baseline-gpu-640x480-60` |
| カメラ要求 | インカメ、640×480 |
| フレームレート要求 | 30fps以上、最大60fpsを希望 |
| 手の認識処理 | GPU優先 |
| 同時に認識する手 | 2手 |
| 検出・存在・追跡の基準値 | すべて0.5 |
| ライブラリ | `@mediapipe/tasks-vision@0.10.35` |
| モデル | `hand_landmarker/full/float16/1#fbc2a30080c3` |

これはアプリから端末へ要求する条件であり、端末が実際に出した解像度やfpsを保証する値ではない。実際の値は結果JSONへ別に記録し、要求との差も試験結果として扱う。GPU初期化に失敗してCPUへ切り替わった場合も隠さず記録し、通常のGPU実測と同一扱いにしない。

各端末の最初のセッションでは、profile、アプリbuild、ジェスチャー閾値を変更しない。比較条件を試す場合は、基準条件の結果を保存した後、新しいsessionIdで変更点を一つだけ選ぶ。

### 3.2 5動作・50試行のプロファイル

2026-09-14以降の5動作・50試行は、[13_p1_five_gesture_50_trial_revision_plan.md](./13_p1_five_gesture_50_trial_revision_plan.md)の11章に従い、iPhone SafariとAndroid Chromeで同じbuild・profile・閾値を使う。profileは、テスター画面で選択操作が要らない画面の既定値`gpu-640x480-30`を使う。この選択は2026-09-14時点の手順案であり、実測前に変える場合は本節を更新する。

60fpsの基準プロファイルで比べる場合は、両端末のURLへ`?profile=baseline-gpu-640x480-60`を付けて開き、30fpsの結果とは別のsessionIdとして記録する。標準のテスター画面にはプロファイルの選択欄を表示しないため、選択はURLで行う。`?view=analysis`で開いた画面では、カメラ開始前にLive diagnosticsの「実験プロファイル」でも選べる。

## 4. テスト前チェック

1. そのセッションで指定した実験プロファイルで開いていることを、カメラ開始前に確認する。5動作・50試行では両端末とも同じprofileを使う（3.2）。
2. 端末、OS、ブラウザ、モデル／アプリ版を記録する。
3. Bluetoothが切れていることを確認する。
4. 端末が横向きで安定し、プレイヤーが画面を無理なく見られることを確認する。
5. 左右の手を胸〜肩の高さで広げ、両方が快適領域へ収まることを確認する。
6. 生映像を保存しない設定を確認する。
7. 開発ログの時刻、端末時刻、試行番号を確認する。
8. テスターへ「成功させることより、感じたずれや誤認識をそのまま伝えることが重要」と説明する。

標準画面は「はじめる」の1ボタンで、音声、カメラ、試験を順に開始する。`?view=analysis`では「カメラを開始」「テストを開始」の2操作を残す。選んだ向きのまま進める。以後は5.6のとおり、同じ動作の中の試行は約1秒で自動で進み、動作の切り替わりと最初の試行は画面のタップで進む。端末を比較する際は同じ向きにそろえる。

## 5. Phase 1 — 制御試験

2026-09-19以降の定例の試行は、成立確認が残っているribbon-swipeとBloomの各10回、合計20回とする（手順ID `p1-remaining-two-20`）。air-tap、Lift、Spotlightは両端末で8/10以上を満たし、成立確認を終えた（[18](./18_android_second_test_and_next_plan.md)の3章）。試験手順はURLで選ぶ。

| URLの指定 | 手順ID | 内容 |
|---|---|---|
| なし（既定） | `p1-remaining-two-20` | ribbon-swipe 10回、Bloom 10回。試行の定義と順序は5動作版の同じ動作と同一 |
| `?protocol=five` | `p1-five-gesture-50` | 下表の5動作・50試行 |
| `?protocol=regression` | `p1-regression-three-9` | air-tap、Lift、Spotlightを各3回。判定の時間定数または座標の扱いを変えた後の回帰確認に使う。目安は3回中3回 |

手順IDが違う結果は同じ表へ混ぜない。20回版と回帰確認版は、3入力がそろわないため単独ではP1-Controlledの合否候補にしない。

2026-09-14以降のPhase 1は、5動作を10回ずつ行う5ブロック・合計50試行とする。改訂の計画と根拠は[13_p1_five_gesture_50_trial_revision_plan.md](./13_p1_five_gesture_50_trial_revision_plan.md)に記録している。左右・方向の偏りを避けるため、全テスターで次の順序を使う。順序効果が疑われた場合だけ、別セッションで候補動作の順序を反転する。

| ブロック | 動作 | 試行数 | 合図前の準備 | ブロック後 |
|---:|---|---:|---|---|
| 1 | air-tap | 10 | なし | 次の動作の案内を出し、画面のタップで進む |
| 2 | ribbon-swipe | 10 | なし | 次の動作の案内を出し、画面のタップで進む |
| 3 | Bloom | 10 | 中央準備の完了を待つ | 次の動作の案内を出し、画面のタップで進む |
| 4 | Lift | 10 | 下側開始位置の完了を待つ | 次の動作の案内を出し、画面のタップで進む |
| 5 | Spotlight | 10 | なし | 完了 |

50試行は5動作すべてを製品へ採用する決定ではない。air-tap、ribbon-swipe、BloomはMVPの3入力としてP1-Controlledの出発点（各8/10以上）に使う。Lift／Spotlightは候補動作であり、成功率、誤発火、タイミング、疲労、分かりやすさを比べてInteraction POCへ持ち込む3〜4動作を選ぶ材料にする。P1-Controlledの合否条件には含めない。

各ジェスチャーを説明・実演した後に始める。標準画面では、現在の試行の始める位置、道筋、終点をカメラ映像の上に判定と同じ座標で描き、`GO`と同時に光の点が道筋を進む（[04の3.1](./04_mvp_uiux_direction.md)）。プレイヤーはカウント音と映像の中央の`GO`を時刻の基準にする。光の点の速さは目安であり、判定時刻を表さない。

各試行は、カウント中の準備期間とrecognition windowを分ける。音声targetがある場合は`targetTimeMs - 500ms`からイベントと拒否理由を採用し、deadlineは`targetTimeMs + 10,000ms`とする。音声targetがない場合は試行開始時刻をwindow開始とし、そこから10秒をdeadlineとする。準備完了を待つ試行（Bloom／Lift）では、試行開始時刻の代わりに準備完了時刻（`readyAtMs`）を基点にする。準備期間の開始位置合わせや拒否は試行結果へ加えない。

10秒は、合図を見てすぐ行う単体ジェスチャーを数回試せる上限として使う。実機で準備と1回の動作を終える時間が足りないと確認できた場合だけ、別セッションで13秒を比較する。同じセッションの途中では変更しない。

期待ジェスチャーが成立しない場合も試験を停止し続けない。根拠を確認できる場合は手動分類し、判断できない場合は「反応しなかったので次へ」を選ぶ。手動分類の操作は`?view=analysis`の画面にだけあり、その画面では同じボタンを「未成立として次へ」と表示する。deadlineへ到達した試行は自動で次へ進む。deadlineの直前に撮ったフレームは推論の分だけ遅れて届くため、画面はdeadlineから200ms待ってからtimeoutを確定し、完了時刻はdeadlineとして記録する。deadlineより後に撮ったフレームは判定に使わない。手動スキップとtimeoutはいずれも`unclassified`として完了件数と各ジェスチャー10回の分母へ含め、解決経路をそれぞれ`manual-skip`、`trial-timeout`として記録する。timeoutだけを根拠に`player miss`または`machine miss`へ分類しない。

結果が決まった後は（成立、手動分類、手動スキップ、timeoutのいずれでも）約1秒だけ結果を表示し、同じブロックの次の試行を新しいtargetで準備する。ブロックの最後の試行が終わった後は自動で進まない（5.6）。ページ非表示中とカメラ停止中に試行を消化しない。自動で中断する条件と、止めた試行のやり直しは5.6に従う。

### 5.1 エアタップ 10回

- 左側5回、右側5回を交互に行う。
- ターゲット面を通過し、止めたままにしない。
- 案内では、指定側の人差し指がリングの外の丸印からリングの中へ通過することを示す。
- 各試行の間にクールダウン表示を待つ。

### 5.2 リボンスワイプ 10回

- 左→右、右→左を各3回。
- 左下→右上、右下→左上を各2回。
- 案内では、片手の開始位置の丸印、帯に沿う道筋、終点の輪を示す。
- 指定方向、中心通過、成立時刻を別々に記録する。
- 逆方向（`wrong-direction`）は、進行方向へ0.02を超えて後退したときだけ出す。1フレーム差分の速度は使わない（2026-09-19、根拠は[19](./19_android_third_test_and_recognition_fixes.md)の3.1と4.2）。
- 追跡の途切れの許容は「150msと、直近15区間のフレーム間隔の中央値の2.5倍の、大きいほう」で、上限は400msとする。毎秒30回前後の端末では150msのまま、毎秒約10回の端末では約250msになる（2026-09-19、根拠は[19](./19_android_third_test_and_recognition_fixes.md)の3.1）。Bloom、Lift、Spotlightと、追跡側のtrackの保持にも同じ値を使う。使った値の最小と最大は結果JSONの`performance`の`trackingGapToleranceMs`に残る。

### 5.3 Bloom 10回

- 中央寄りの準備姿勢から開始し、両手をそれぞれ外側かつ斜め上へ開く。
- 中央準備ゾーンは、正規化座標で両手の中点がx 0.28〜0.72、y 0.25〜0.75に入り、両手の間隔が0.10〜0.42であることとする（実測前の初期値。2026-09-14の実装から変えていない）。カメラ上の案内と動きの見本は、この値から描く。案内の始点の丸印は、腕の負担を減らすため、範囲の下限より0.09上のy 0.66に置く。準備が整った後は、道筋と終点の輪を、実際に手が止まった位置から描き直す（2026-09-19、[19](./19_android_third_test_and_recognition_fixes.md)の3.2と4.3）。
- 試行を表示した時点ではカウント音を予約しない。両手が中央準備ゾーンに入り、最初の位置から0.05を超えて動かずに約200ms安定した時点を準備完了（`readyAtMs`）とし、その後にカウント音と`GO`を予約する。準備中の動き、拒否、追跡喪失は試行結果へ加えない。
- 準備が10秒以内に完了しない場合は`unclassified`、解決経路`trial-timeout`、reason `readiness-timeout`とする。recognition windowのtimeoutとは`timeoutPhase`（`readiness`／`recognition`）で区別する。
- 準備位置で`GO`を待つ間は、Bloomの動作時間の上限（1.4秒）を消費しない。両手が待機位置から正規化座標で0.02以内にある間は待機中とみなし、上限はそこから動き出した時点から数える。待つ間に手が少しずれて止まった場合も、両手が約0.25秒のあいだ0.02以内にとどまり、中央準備ゾーンの中にあれば、その位置を新しい待機位置にする。0.25秒で0.02より大きく動く動き（毎秒約0.08以上）は待機とみなさない。距離・速度・同期幅の閾値は変えない。
- 拒否や追跡喪失の後は、両手が中央準備ゾーンの中で約0.25秒止まってから次の判定を始める。手を中央へ戻す動きを、内向き・下向きの拒否として続けて数えないためである。recognition windowで最初に両手が映ったフレームだけは、準備完了を確認済みなので、止まるのを待たずに判定を始める。
- 追跡側が左右の手のIDを入れ替えた場合は、画面上の位置で左右を付け直して判定を続け、入れ替わりの回数（`identitySwapCount`）を診断へ残す。プレイヤーの動きの拒否として数えない。
- 実接触、クラップ音、マイク許可を要求しない。音声はゲーム時刻の基準として使うが、Bloom成立条件には使わない。
- 左右どちらかが先に終点へ到達しても、もう片方が同期幅内に到達すれば成功とする。左右の開始・終了順を固定しない。
- 準備中に先行して開いた動きは、recognition window開始時に持ち越さない。中央準備を新たに成立させてから判定する。
- 短い追跡欠落は同じ候補を継続し、長い欠落は`tracking-lost`を一度だけ記録して再アームする。追跡喪失をプレイヤーMISSへ分類しない。成立前の拒否件数（`rejectionCount`）にも数えず、追跡喪失の件数（`trackingLossCount`）として分けて記録する。欠落の記録は、両手が再び映った時点で閉じる。
- 拒否・不成立は、内向き、下向き、外向き距離不足、上向き距離不足、同期幅超過、外向きの速さ不足（`movement-too-slow`）、距離は足りたまま時間上限を超えた場合（`candidate-timeout`）を分けて記録する。
- 片方の手が外向きと上向きの必要量に達した時刻は固定する。どちらかの量が必要量より0.03を超えて戻った場合だけ、到達を取り消す。
- 0.05、0.02、約0.25秒、0.03は実測前の初期値である。
- 成立時刻は描画フレーム番号ではなく`captureTime`を使い、ランドマーク軌跡の閾値通過をフレーム間補間して`eventTime`へ保存する。
- 案内は、左右2つの丸印と、左右斜め上の輪へ伸びる二本の道筋で示す。強さや腕の絶対距離を評価しない。別枠の動作見本（中央の光球と二本の軌跡）は`?view=analysis`の画面にだけ残る。

### 5.4 Lift 10回（候補動作）

- 両手を画面下側の左右の開始ゾーンへ置き、最初の位置から0.05を超えて動かずに約180ms安定したら準備完了とする。0.05を超えて動いたら安定の計測をやり直す。準備完了後の合図と`readiness-timeout`の扱いはBloomと同じで、Liftの準備timeoutにはreason `lift-not-ready`を併記する。
- `GO`の後、左右の手をほぼ平行に真上へ上げる。両手が正規化座標で0.18以上上がり、左右が上昇量に達した時刻の差が420ms以内なら成立とする。成立時刻は、遅い方の手が上昇量に達した時刻を`captureTime`の間で補間して求める。
- 腕の絶対的な高さや速さは評価しない。端末画面上の正規化座標に対する移動量で判定する。
- 拒否理由は`lift-not-ready`（開始位置にない）、`lift-not-upward`（下向き、または横方向が主の動き）、`lift-distance-insufficient`（上昇量不足）、`lift-sync-expired`（左右の到達時刻差が同期幅を超えた）、`tracking-lost`に分ける。
- 開始ゾーンは画面下側（正規化座標でy 0.58〜0.97）の左右に置く。左手はx 0.03〜0.47、右手はx 0.53〜0.97の範囲とし、両手の間隔を0.12以上とする。
- 横方向の移動が0.14を超え、かつ上昇量より大きい場合は`lift-not-upward`とする。
- Bloomと同じく、待機位置から0.02以内にある間は待機中とみなし、動作時間の上限（1.4秒）は動き出した時点から数える。ずれて止まった場合の待機位置の付け直し、拒否後に約0.25秒止まってから判定を再開すること、左右IDの入れ替わりの扱いもBloomと同じとする。上限を超えても上昇量が足りない場合は`lift-distance-insufficient`とする。
- `lift-not-ready`は、recognition windowで最初に両手が映ったフレームで判定し、1回だけ記録する。
- 先に上がった手が必要な上昇量（0.18）の付近で揺れても、上昇量に達した時刻は最初に達した時刻のままにする。必要な上昇量より0.03を超えて下がった場合だけ到達を取り消す。
- 0.18、420ms、0.14、1.4秒、開始ゾーンの範囲、0.05、0.02、約0.25秒、0.03は実測前の初期値である。

### 5.5 Spotlight 10回（候補動作）

- 画面に指定の対角配置を表示し、`GO`の後に片手を上側ゾーン、反対の手を下側ゾーンへ移動して約300ms止める。
- 左手上／右手下を5回、右手上／左手下を5回、交互に行う。左右はプレビューの見た目（鏡像）で判定し、画面左側の手をプレイヤーの左手とする。
- 保持が成立した場合の`eventTime`は、両手が指定ゾーンへそろって入った最初の`captureTime`とする。保持確認の約300msを遅延として加えない。
- recognition windowが開く前（`GO`の500ms前より前）のカウント中に指定の形を作り、ほどかないままwindowが開いた場合は成立させず、reason `spotlight-pose-before-go`を一度だけ記録する。windowが開いてから`GO`までの500msに作った形は、ほかの動作と同じく早めの成立として受け付ける。境界のフレームで片手しか映っていなくても、カウント中に作った形は覚えておき、windowで最初に形が見えたフレームで判定する。一度形をほどいてから作り直した時点を新しいゾーン侵入として扱う。これは`GO`の後のゾーン侵入時刻を測るための実装上の決定である。音声targetがない試行では、試行開始時の最初のフレームをカウント中の形として扱う。
- 形が崩れたと判断するのは、別の形が60ms以上続いた場合とする。1フレームだけゾーン境界を越えるランドマークの揺れでは保持を切らず、ゾーン侵入時刻も変えない。形をほどいたかどうかと、逆の形を約300ms保持したかどうかの判断にも同じ猶予を使う。
- 左の手はx≦0.5、右の手はx≧0.5に置き、両手の間隔を0.1以上とする。この条件を外れた形が約300ms続いた場合は、reason `spotlight-hands-not-separated`を一度だけ記録する。
- 拒否理由は`spotlight-pose-not-held`（約300ms保持する前に形が崩れた）、`spotlight-wrong-side`（上下が指定と逆の形を保持した）、`spotlight-wrong-zone`（両手が同じ高さのゾーンにそろった）、`spotlight-hands-not-separated`（両手が中央の線の両側に分かれていない）、`spotlight-pose-before-go`、`tracking-lost`に分ける。
- 上側ゾーンは正規化座標でy≦0.42、下側ゾーンはy≧0.58とする。約300ms、60msの猶予とあわせて実測前の初期値とする。

### 5.6 ブロック進行・中断

- 各ブロックの最後の試行が終わったら次のブロックを開き、次の動作の案内と「画面をタップして開始」を表示して、画面のタップを待つ。タップしたら最初の試行へ進む。必須の休憩は設けない。案内を出してから0.4秒間はタップを受け付けない。タップを待つ時間は試行のtimeoutとジェスチャー時刻へ含めない。待っている間も中断を受け付けるため、ブロックは案内を出した時点で開始する。このため`restBeforeMs`はほぼ0になり、タップを待つ時間はそのブロックの記録時間と`performance`のブロック別の集計に含まれる。待っている間も「中断」、ページ非表示、カメラ停止で止まり、再開後は次の試行から進む。最初の試行も同じ作法で、画面のタップで始める。
- ブロックの途中では「中断」で止められる。ページが非表示になった場合と、カメラが止まった場合（「カメラを停止」や映像の途切れ）も自動的に中断する。試行と試行の間（結果表示の約1秒）に非表示になった場合も同じである。中断時に進行中だった試行は結果へ加えず、「再開」を押した後に同じ試行を最初からやり直す。カメラが止まっている間は「再開」を押せない。
- 中断時間は試行のtimeoutやジェスチャー時刻へ含めない。中断したときは、予約済みのカウント音も止める。
- 「中断」「再開」は表示が切り替わってから0.4秒間は押しても反応しない。素早い2回押しで、中断した直後に再開しないためである。
- 「再開」を押したときは、止まっている音声を再開する。再開を待つのは最長0.6秒とする。音声が動いていない場合と、音声の時計から求めた`GO`までの時間が1秒未満または4秒超の場合は、その試行をカウント音なしで進め、画面にその旨を表示する。止まった音声の時計から`GO`を過去の時刻に予約しないためである。音声を使えない端末では、すべての試行をカウント音なしで進め、同じく画面に表示する。
- 結果が1回以上ある状態で「テストを最初からやり直す」を押した場合は、結果を消してよいか確認する。
- 結果JSONには、ブロックごとの開始・終了時刻、前のブロックからの休憩時間、中断の開始・再開時刻と理由、やり直した試行IDを残す。試行結果には何回目の試み（`attempt`）かを残す。

旧clapを含むschema v2／v3の結果JSONと、3入力・30試行のschema v4の結果JSONは引き続き読み込める。現行の標準JSONはschema v7で、実行した手順のID（既定は`protocol.id = "p1-remaining-two-20"`）、`protocol.trialsPerGesture = 10`、`gestureVocabulary.gestures`（実行した動作。既定の`p1-remaining-two-20`ではribbon-swipeとBloomの2つ）を明示する。旧clap、v4のBloom、v5以降の5動作は語彙とprotocol IDで区別し、同じ第三入力や同じ試験条件の結果へ混ぜない。schema v6とv7はv5へ記録項目を足した版で、判定条件と合否の計算はv5と同じである。2026-09-19の画面改訂から必須休憩をなくしたことは、ブロックのrestAfterとセッションのメモで区別する。v5とv6のファイルは、足した項目を「記録なし」または当時の既定値として読み込み、同じ手順IDの結果として比較できる。

- 音声の状態と時刻の対応方式、`baseLatency`と`outputLatency`、描画fps、手の初回取得時間、フレームの取得方式（カメラ計測用の`cameraFrameSource`と追跡用の`trackingFrameSource`）、画面を消さない仕組み（Screen Wake Lock）の取得結果（`environment`、schema v6）。`screenWakeLock`は`not-requested`／`unsupported`／`acquired`／`denied`のどれかで、セッション中に一度でも取得できた場合は`acquired`とする。保存時点で保持していたことは意味しない
- 端末の情報（`technicalSnapshot.device`、schema v7）。テスターに入力させず、ブラウザが公開する値を自動で集める。Chrome系は`navigator.userAgentData`から機種名、OSと版、ブラウザと版を取る。全ブラウザで、CPUの論理コア数、画面の大きさと画素密度、GPU名（`WEBGL_debug_renderer_info`）、言語、タッチ点数を取る。Chrome系だけで、メモリの目安と、開始時・保存時の電池の状態を取る。取得できない値は`null`とし、Safariの機種名のように公開されない値を推測で埋めない。位置情報、固有ID、フォントの列挙は取らない。値は利用者が保存する結果JSONにだけ入り、送信しない
- 処理経路の指定（schema v7）: `technicalSnapshot.frameSourceOverride`（`?frameSource=`の指定。`auto`／`rvfc`／`timer`）、`technicalSnapshot.pendingPolicy`（`?pending=`の指定。`hold`／`drop`）、`technicalSnapshot.droppedFrames`と`performance`の`scheduler.dropped`（`drop`で捨てたフレーム数）。実際に動いた経路は`technicalSnapshot.frameSource`に残る。指定が違うセッションは同じ条件として比べない
- メインスレッドの長い処理の上位3件（`performance`の`longTask.longest`、schema v7）: 開始時刻、長さ、取得できる場合は発生元
- ID swapと理由コード
- 各試行の準備、準備完了（`readyAtMs`）、window開始、target、deadline、完了時刻
- 準備のtimeoutとrecognitionのtimeoutの区別（`timeoutPhase`）、成立前の拒否件数（`rejectionCount`）、同じ区間の追跡喪失の件数（`trackingLossCount`）、試みの回数（`attempt`）
- 準備が完了しなかった理由（`readiness-hands-missing`：両手がそろって映らなかった、`readiness-outside-zone`：開始位置の枠に入らなかった、`readiness-not-still`：止まらなかった）と、準備中の観測の要約（`readinessDiagnostic`）。recognition windowが開かなかった試行には、動作の判定器の診断を保存しない
- 準備時間のp50／p95は準備が完了した試行だけから求め、準備のtimeoutは`readinessTimeout`として別に数える
- 中断で捨てた試みの拒否理由と自動の誤発火は、結果の集計（`diagnosticReasonCounts`、`falseTriggers`）から外し、`abandonedAttemptReasonCounts`と`abandonedFalseTriggers`に分けて残す。テスターが押した「意図せず反応した」は捨てずに数える
- 診断リプレイはschema v3で保存し、準備だけで終わった試行と中断で捨てた試みの区間も記録する。旧v1／v2も読み込める
- ブロックの開始・終了・休憩時間と中断の記録
- Spotlightの左右variant、成立に採用したゾーン侵入時刻と保持完了時刻
- 解決経路（gesture event、手動分類、手動スキップ、trial timeout）
- 試行別の拒否理由とtracking gap。schema v6では、同じ試行・同じ試み・同じ手・同じ理由の記録が連続した場合に1件へまとめ、回数（`count`）と最後の時刻（`lastTimeMs`）を持たせる。理由別の件数は`count`を足して数える
- app build ID、実験profile ID、要求したカメラ／delegate／model設定
- ブラウザが実際に選んだ解像度／fps／frame source／delegate／model

同一セッション中に実験profileを変更しない。設定を変更する場合は新しいsessionIdで記録し、変更前後を同じ結果表へ混ぜない。

## 6. Phase 2 — Interaction POC試験

短い統合シーケンスを、各テスターが同じ端末条件で3回行う。

## 7. Phase 3 — M1-Web MVP品質試験

90秒MVPが完成した後、5人テストへ出す前に実施する。

1. 各ジェスチャーを各端末で20回以上行い、controlled recall 95%以上を確認する。
2. 90秒MVPを同じ設定で繰り返し、連続10分以上動作させる。
3. 10分中のfalse trigger、二手coverage、追跡Hz、frame age p95を集計する。
4. 開始時と終了時のメモリ、フレーム待ち行列、推論p50 / p95を比較する。
5. 10分後も入力品質が階層を跨いで低下しないことを確認する。
6. 一項目でも満たさない場合は、M1をPassにせず、Learnとして原因と次の変更を一つ記録する。

## 8. 分類ルール

| 分類 | 定義 | 判定方法 |
|---|---|---|
| success | 期待ジェスチャーが成立し、イベント時刻が記録された | イベントログ |
| player miss | 指定方向、位置、順序、時刻等をプレイヤーが満たしていない | ランドマーク再生＋譜面条件 |
| machine miss | 参照条件を満たす軌跡があるのに正しいイベントが出ない | ランドマーク再生＋reasonCodes |
| false trigger | 対象操作をしていないのにイベントが出る | イベント前後の派生軌跡 |
| tracking loss | 必要な手が追跡できず判定不能 | trackingConfidenceと欠落時間 |
| unclassified | ログだけではplayer／machineを区別できない | 推測でどちらかに寄せない |

`unclassified`を除外して成功率を良く見せない。手動スキップとtrial timeoutも各ジェスチャー10回の分母へ含め、件数、解決経路、原因をそのまま残す。成功、手動分類、手動スキップ、timeoutが競合した場合は、最初に確定した結果だけを一件記録する。

複数P1 JSONの自動比較は、試験手順ごとの試行数（3入力版30、5動作版50、残る2動作版20、回帰確認版9）とブロック数、各ジェスチャーの試行数（回帰確認版は3、他は10）、分類合計、privacy、build／profile／protocol条件、技術値の不備を検出するために使う。同じsessionIdのファイルは、同じ試験を2回保存したものとして1件に数える。全セッションの端末情報（userAgent）が同じ場合と、手の認識処理が要求と違う処理（GPUからCPUなど）で動いた場合は、合否候補にしない。schema v5以降では、試験手順ID、各動作の試行数、5ブロックの記録、`attempt`、Spotlightの左右の割り当て（5回ずつ）も確かめ、合わない場合は合否候補にしない。3入力が8/10以上でも、自動比較だけで`Pass`を確定しない。Lift／Spotlightの成立率は候補動作の比較材料として表示し、P1-Controlledの合否候補には含めない。対象の端末／テスター組み合わせ、手動分類、同期感、観察記録を確認して最終判定する。
