# 構造の見直しと判定に触れない修正の記録

- 作成日: 2026-09-19
- 更新日: 2026-09-19
- 文書種別: 構造レビューの結果と実装記録（仕様の正本ではない）
- ステータス: **段階Aと段階Bを実装済み。自動検証は完了。実機（iPhone Safari、Android Chrome）では未確認。段階Cと段階Dは未着手**
- 対象: Technical Labの画面側の処理、結果JSONの記録、Bloomの案内、映像枠
- 関係する正本: [05_poc_test_protocol.md](./05_poc_test_protocol.md)の5.6と5.7（結果JSONの版と記録項目）、[02_technical_strategy_and_plan.md](./02_technical_strategy_and_plan.md)（アーキテクチャと計測）

## 1. 目的

「アプリが重くなっていないか」「画面の作りや判定の仕組みが原因で手の認識がおかしくならないか」「構造を作り直す必要があるか」を、コードと実測記録から確かめた。そのうえで、Android Chromeの実測より前に入れてよい修正（判定条件を変えないもの）だけを実装した。

## 2. レビューの結論

作り直しは要らない。カメラ取得、latest-frame-onlyのスケジューラ、Workerでの推論、追跡バックエンドと判定の分離、ミリ秒基準の判定、成立時刻の補間、追跡喪失とプレイヤーのミスの分離は、[02](./02_technical_strategy_and_plan.md)の設計どおりに実装されている。

一方で、次の3種類の弱点を確認した。

1. 判定の座標が、映像の縦横比と端末の向きで意味を変える。
2. 画面側が、毎フレームやらなくてよい処理をしていた。
3. 保存される性能値が保存直前の約6秒分だけで、セッション全体の重さを後から判断できなかった。

### 2.1 実測から見た重さ

- iPhone Safari（[14](./14_p1_session_analysis_20260916063846360.md)）: 追跡29.15Hz、推論p50 / p95 27.0 / 50.1ms、frame age p95 67.1ms。基準内である。
- Android Chrome（[11](./11_phase1_trial_progression_and_swipe_reliability_plan.md)の3.3と12.1）: 追跡8.36Hz、改善後13.68Hz。frame age p95 316.6ms、改善後255.2ms。基準を割っている。ただしどちらも旧build、旧profileの記録である。改善前（8.36Hz）は全フレームを結果JSONへ埋め込む旧schema v2で、記録の負荷が混ざっている可能性がある。改善後（13.68Hz）は診断を別ファイルへ分けた後の記録である。原因は未特定である。
- どちらの値も、保存直前の直近180サンプルの値である。

### 2.2 判定側で確認した問題（未修正。段階C）

| 問題 | 確認した場所 | 利用者から見た症状 |
|---|---|---|
| 映像の縦横比を補正していない | `src/tracking/hand-feature-pipeline.ts`の速度と距離、各状態機械の閾値。判定側は`videoWidth`／`videoHeight`を参照しない | 同じ大きさの動きでも、横と縦で成立しやすさが違う。640×480と480×640で同じ閾値の意味が変わる |
| リボンスワイプの逆方向判定が1フレーム差分の速度を使う | `src/gestures/ribbon-swipe-state-machine.ts`の`directionalSpeed < -0.08` | 追跡結果の通常の揺れで候補が取り消される。iPhone実測で`wrong-direction`が43件 |
| 手の大きさで閾値を割っていない | `handScale`は`hand-feature-pipeline.ts`で計算されるが、判定では未使用 | カメラから遠い人、手の小さい人ほど成立しにくい |
| 追跡が150msを超えて切れると候補を捨てる | 各状態機械の`maximumTrackingGapMs` | Bloomでは準備位置へ戻して250ms静止し直す必要があり、1回の見失いで約2秒かかる |
| 複数動作の同時判定が未検証 | `GestureArbiter`はテストからだけ呼ばれる。P1は1試行につき判定器1つ | P1の「誤反応0件」は、他の動作の判定器を動かしていない状態の値である |
| BloomとLiftの実装がほぼ複製 | `bloom-state-machine.ts`と`lift-state-machine.ts` | 片方の修正をもう片方へ入れ忘れやすい |

これらは判定の物差しを変えるため、両端末の実測後、Interaction POCへ入る前に扱う。

## 3. 実装した修正

判定条件、試行の進行、合否の計算は変えていない。`src/gestures/`の差分は、Bloomの定数表を`BLOOM_DEFAULTS`という名前でexportしたこと（宣言、参照1か所、説明コメント）だけで、値とロジックは同じである。`src/poc/phase1-protocol.ts`の差分は、Bloomの指示の文言1行だけである。

### 3.1 画面側の処理を減らす（段階A）

- 重ね表示canvasの画素密度に上限2を設けた。iPhone（画素密度3）で描く画素数が約56%減る。
- 重ね表示は、追跡フレーム、案内、表示設定、canvasの大きさ、映像の実寸のどれかが変わったときだけ描き直す。変更前は毎秒60回、無条件に全消去して描いていた。canvasの大きさは`ResizeObserver`で受け取り、非対応の環境では従来の方式へ戻る。
- `LabView`の文字の書き換えは、値が変わったときだけ行う。診断パネル内の計測値は250msに1回へ間引いた。状態カード、ボタン、追跡状態の帯は間引かない。
- `TrackingMetricsCollector`のパーセンタイル等の再計算を250msに1回へ間引いた。最新フレーム、手の数、状態は毎フレーム更新する。
- パネルの`backdrop-filter`をすべて外し、背景の不透明度を上げた。横向き時に映像の上へ重なる状態カードも同じである。
- プレビューを隠す指定を`filter: brightness(0)`から`opacity: 0`へ変えた。映像は描画可能なまま残るので、`requestVideoFrameCallback`による追跡は続く（ブラウザ自動試験で確認）。
- 結果JSONの保存時に、記録した全フレームを複製していた処理をなくした。保存に使うのは件数だけだった。リプレイ記録の1フレームあたり2回の複製も1回へ減らした。

### 3.2 計測の穴を埋める（段階A）

結果JSONをschema v6へ上げ、次を追加した。記録項目の正本は[05](./05_poc_test_protocol.md)の5.7である。

- `performance`: セッション全体と5ブロックそれぞれの性能値。1ms刻み・1000区間の固定ヒストグラムで集計するので、メモリは約96KBで一定である。p50 / p95は1ms単位、最大値は正確な値を別に持つ。
- `trialEnvironments`: 試行ごとの画面の向き、viewport、映像の実寸。
- `environment`: 音声の`baseLatency`／`outputLatency`、描画fps、手の初回取得時間、フレームの取得方式、Screen Wake Lockの取得結果。
- `measurementNotes`: 既存の`technicalSummary`と`technicalSnapshot`が直近180サンプルの値であることの注記。
- `trialDiagnostics[]`の`count`と`lastTimeMs`: 連続する同じ記録を1件へまとめる。実際にまとめが効くのは、毎フレーム出る`identity-conflict`である。拒否の理由コードは判定の試みごとに1件なので、件数は従来と同じになる。

既存の項目は名前も意味も変えていない。v5以前のファイルは、追加項目を「記録なし」として読み込める。セッション比較の指摘と合否候補の計算は変えていない。`scripts/analyze-p1-confidence.mjs`は`count`を展開して数えるよう直した。

追加した値は結果JSONにだけ出る。画面と比較表には表示していない。

### 3.3 画面を消さない（段階A）

`src/app/screen-wake-lock.ts`を追加した。テスト開始、ブロック開始、再開でScreen Wake Lockを取得し、中断、全ブロック完了、画面破棄で解放する。非対応と拒否は例外にせず、結果を`environment.screenWakeLock`へ残す。ページ非表示による中断の挙動は変えていない。

### 3.4 Bloomの案内を判定条件に合わせる（段階B）

- 変更前は、カメラ上の案内が旧clap用の表示（中央の丸と、x=0.3／0.7からの線）のままだった。判定が求める準備範囲は描かれていなかった。
- 変更後は、`BLOOM_DEFAULTS`から計算した枠（両手の中点が入る範囲）と、左右の手の目標位置（x 0.37と0.63、間隔0.26）を描く（`src/rendering/bloom-guide.ts`）。準備範囲の数値の正本は[05](./05_poc_test_protocol.md)の5.3である。
- 動きの見本（CSS）の開始位置を、左46%／右54%（間隔0.08で判定の下限0.10を割る）から、左37.5%／右62.5%（間隔0.25）へ直した。`tests/bloom-guide.test.ts`が、CSSの開始位置が判定の許容範囲に入ることを検査する。
- 文字の指示も案内に合わせた。試行の指示は「両手を離して画面中央の左右の丸印に合わせて止め、GOで左右斜め上へ開く」で、準備待ちの案内と動作見本の説明も同じ趣旨にした。変更前の「両手を中央の光に構えて止め」は、両手を寄せる動きに読めた。

**比較上の注意**: 判定条件は同じだが、プレイヤーの構え方が変わる。この修正より後のBloomの成立率は、[14](./14_p1_session_analysis_20260916063846360.md)の6/10と単純比較しない。

### 3.5 映像枠を映像の縦横比に合わせる（段階B）

`.preview-shell`の縦横比を、映像の実寸から設定する（`--video-aspect`）。高さに上限がある画面では、幅を縮めて縦横比を保つ。変更前は、縦持ち（映像480×640）のときに`object-fit: cover`が映像の上下を切り取り、案内の枠が画面外へ出ていた。座標変換（`createVideoCoverTransform`）は変えていない。

高さ520px以下の横向きの画面では、映像枠が従来より小さくなる（高さ148pxの上限のまま縦横比を保つため）。

## 5. 未決事項

1. 解決済み（2026-09-19）。Bloomの文字の指示は「両手を中央の光に構えて止め」で、両手を寄せる動きに読めた。試行の指示を「両手を離して画面中央の左右の丸印に合わせて止め、GOで左右斜め上へ開く」へ直し、準備待ちの案内と動作見本の説明も同じ趣旨へそろえた（`src/poc/phase1-protocol.ts`、`src/poc/phase1-lab-controller.ts`）。判定条件は変えていない。
2. 直近窓の値（補間つき）と、全体・ブロック別の値（1ms刻みの順位方式）でパーセンタイルの求め方が違い、数msずれることがある。
3. ブロック別の性能値は、ブロック内の中断時間を含む。
4. 動作見本のアニメーションは`top`／`left`を動かす方式のままである。2026-09-19に標準画面から別枠の動作見本を外したので、影響があるのは`?view=analysis`の画面だけになった。`transform`方式への書き換えは未着手。
5. 段階C（縦横比の補正、スワイプの逆方向判定、手の大きさでの正規化、見失い後の継続）と段階D（全動作の同時判定と調停、BloomとLiftの共通化）は未着手。
