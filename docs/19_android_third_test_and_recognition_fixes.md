## 2. テスターの報告

1. 当たり判定の部分が小さすぎる。
2. 両手を左右に開く動作（Bloom）は腕が疲れる。もう少し低い位置にするなどの工夫がほしい。

## 3. 診断リプレイから分かったこと

### 3.1 正しく動かしても反応しない試行がある

成立した17試行でも、目標時刻からの遅れのp50はribbon-swipe 1514ms、Bloom 4217msだった。1回目の動作で成立せず、2回目か3回目で成立している。拒否の記録がない試行も多い。

`bloom-3`の記録:

- `GO`の後、両手は(0.36, 0.51)と(0.62, 0.51)で静止していた。
- +530msのフレームの次が+686msで、間隔が156msだった。この時点で`tracking-lost`が記録された。
- +936msから+1400msに、両手は(0.18, 0.37)と(0.81, 0.36)まで動いた。外へ0.18と0.19、上へ0.14で、成立の閾値（外へ0.16、上へ0.08）を満たしている。しかし成立しなかった。
- 成立は3回目の動作の+5633msだった。

原因は、時間の定数が毎秒約30回を前提にしていることである。

- `src/tracking/hand-feature-pipeline.ts`は、手を最後に見てから150msを超えるとtrackを消す（`missingGraceMs`）。手が映り続けていても、フレームの間隔が150msを超えただけでtrackIdが変わる。
- 各状態機械の`maximumTrackingGapMs`も150msである。
- このセッションのフレーム間隔は、p50 99ms、p95 142ms、p99 205msだった。1771区間のうち70区間（4.0%）が150msを超えた。250msを超えたのは15区間（0.8%）だった。
- trackIdが変わると候補は消える。Bloomはその後、準備位置で250ms静止し直すまで動作を受け付けない。テスターから見ると、正しく動かしたのに反応しない。

`ribbon-swipe-9`も同じで、(0.43, 0.58)から(0.67, 0.25)への正しい向きの動作の途中に165msの間隔があり、`tracking-lost`で候補が消えた。

`wrong-direction`は10件あった。[16](./16_structure_review_and_lightweight_fixes.md)の2.2と[18](./18_android_second_test_and_next_plan.md)の2.3で確認済みの、1フレーム差分の速度による逆方向判定である。iPhone 43件、Android 33件に続く3回目の記録になる。

### 3.2 待つ間に腕を下げている

`bloom-5`では、`GO`の時点で両手はy 0.79にあり、`GO`の後にy 0.43まで上げてから開いていた。`bloom-7`も、y 0.68からy 0.45へ上げていた。準備が整ってから`GO`まで約2秒あり、その間、丸印の高さ（y 0.50）で腕を保てずに下げている。テスターの報告2と一致する。

Bloomの準備の判定は、両手の中点がy 0.25〜0.75にあればよい。案内の丸印はその中央のy 0.50に描いている。判定を変えずに、丸印を下へ移せる。

### 3.3 GOより前に動いた試行がある

`bloom-2`と`bloom-4`では、`GO`の約0.7秒前から開き始め、`GO`の時点では終点にいた。その後、始点へ戻ってやり直している。カウントの「2」「1」の間も、道筋と終点の輪が`GO`の後と同じ明るさで見えている。

## 4. 修正

### 4.1 追跡の途切れの許容をフレーム間隔に合わせる（判定の時間定数の変更）

- 許容時間を「150msと、直近のフレーム間隔の中央値の2.5倍の、大きいほう」にする。上限は400msとする。
- 毎秒30回の端末（間隔33ms）では2.5倍が83msなので、150msのまま変わらない。iPhoneの判定は変わらない。
- 毎秒約10回の端末（間隔99ms）では約250msになる。このセッションでは、途切れと扱われる区間が70から15へ減る。
- `HandFeaturePipeline`のtrackの保持と、ribbon-swipe、Bloom、Lift、Spotlightの`maximumTrackingGapMs`の両方へ同じ値を使う。値はフレームごとに追跡側で計算し、判定側へ渡す。
- 根拠: 3.1の`bloom-3`と`ribbon-swipe-9`、フレーム間隔の分布。
- 成立確認を終えた3動作にも効くので、`?protocol=regression`で回帰確認を行う。

### 4.2 ribbon-swipeの逆方向判定を後退距離だけにする（判定の変更）

- `wrong-direction`を、1フレーム差分の速度（`directionalSpeed < -0.08`）では出さず、進行方向への後退距離（`projectionDelta < -0.02`）だけで出す。
- 根拠: 3回の実測（43件、33件、10件）と、[16](./16_structure_review_and_lightweight_fixes.md)の2.2の分析。

[18](./18_android_second_test_and_next_plan.md)の5.6は「1回の試行で変えるのは1動作につき1項目」としていた。ribbon-swipeは4.1と4.2の2項目になる。拒否の理由コード（`tracking-lost`と`wrong-direction`）が別々に記録されるので、効果は分けて読める。実測の回数を減らすことを優先した。

### 4.3 Bloomの案内を低い位置へ移し、手の位置から道筋を描く（判定は変えない）

- 始点の丸印をy 0.50からy 0.66へ下げる。準備の判定の下限（y 0.75）まで0.09の余裕がある。終点は上へ0.14のy 0.52になる。
- 準備が整った後は、道筋と終点の輪を、実際に手が止まった位置から描き直す。判定は止まった位置からの移動量で決まるので、案内と判定が一致する。
- 準備が整うまでの丸印は、目安として大きく描く。
- さらに疲れる場合の次の候補は、準備の判定の範囲を下へ広げること（判定の変更）である。今回は行わない。

### 4.4 丸印と輪を大きくし、GOの前は道筋を暗くする（判定は変えない）

- 始点の丸印と終点の輪を大きく描く。判定は輪の大きさを使っていないので、見た目だけの変更である。
- カウント中は道筋と終点の輪を暗く描き、`GO`で明るくする。3.3の早い動き出しを減らす。

### 4.5 行わないこと

- Bloomの予備動作での拒否（`bloom-not-outward`、`bloom-not-upward`）は今回3件だけだったので、変えない。
- 処理速度の切り分け（[18](./18_android_second_test_and_next_plan.md)の5.5）は、URLの指定を変えた実測を待つ。

## 5. 次の実測

1. 修正後のbuildで、Androidの20回試行を既定の設定で行う。見る値は、成立までの遅れのp50、`tracking-lost`と`wrong-direction`の件数、Bloomの疲れ。
2. `?protocol=regression`で、air-tap、Lift、Spotlightの各3回を確かめる。
3. その後、[18](./18_android_second_test_and_next_plan.md)の6章の順に、URLの指定を変えた20回試行を行う。

## 6. 実装結果

2026-09-19に4.1〜4.4を実装した。4.5の項目には触れていない。試験手順、合否の計算、結果JSONの既存項目は変えていない。

- 4.1: `HandFeaturePipeline`が許容時間を毎フレーム計算し、`TrackedHandFrame.trackingGapToleranceMs`で判定側へ渡す。1000msを超える区間は中央値に入れず、区間が5本そろうまでは150msを使う。各状態機械は、設定値とこの値の大きいほうを使う。値のない合成フレームと古いリプレイでは、今までどおり設定値だけを使う。結果JSONの`performance.session`と各ブロックに`trackingGapToleranceMs: { min, max }`を足した（schema v7のまま、任意項目）。
- 4.2: ribbon-swipeの逆方向判定を後退距離だけにした。動き出しの判定は変えていない。
- 4.3: Bloomの始点をy 0.66へ下げた。準備が整った後は、`ReadinessGate`が返す手の止まった位置から、道筋、終点の輪、光の点を描き直す。Liftも同じ仕組みになった。
- 4.4: 丸印の半径を0.045から0.072へ、輪を0.055から0.088へ大きくした。`GO`より前は、道筋と終点の輪の不透明度を0.25にする。

### 6.1 実機の診断リプレイでの再評価

対象セッションの診断リプレイ（20試行）を、変更前の判定と変更後の判定で再評価した。変更前の再評価は、20試行すべての成立と成立時刻が実機の結果JSONと一致した。再評価の手順が実機の判定を再現できている。

| 指標 | 変更前（実機と同じ） | 変更後 |
|---|---|---|
| 成立 | 17/20（ribbon-swipe 8、Bloom 9） | 19/20（ribbon-swipe 9、Bloom 10） |
| 成立までの遅れ p50（Bloom） | 4217ms | 2215ms |
| 成立までの遅れ 平均（ribbon-swipe） | 2672ms | 2430ms |
| `tracking-lost` | 17件 | 0件 |
| `wrong-direction` | 10件 | 5件 |
| `GO`より前の成立 | 0件 | 0件 |

- `bloom-3`は、1回目の動作の+1297msで成立するようになった（変更前は+5633ms）。`bloom-1`（変更前は不成立）は+1279msで成立した。`bloom-8`と`bloom-10`も1回目の動作で成立した。
- `ribbon-swipe-9`（変更前は不成立）は成立した。`ribbon-swipe-10`は+6373msから+1365msになった。`ribbon-swipe-7`は不成立のままで、拒否は`candidate-timeout`の3件である。
- このセッションで使われた許容時間は、最小150ms、最大268〜327msだった。
- 再評価は記録済みの手の位置を使うので、案内の変更（4.3と4.4）の効果は含まない。テスターの動き方が変わる効果は、次の実測で確かめる。
